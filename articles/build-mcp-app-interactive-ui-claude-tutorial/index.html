Build your first MCP App: an interactive task board that lives inside Claude

Claude can call your tools. What it could not do — until MCP Apps — was show your user an interface instead of a paragraph. This tutorial builds one from scratch: a task board that lives inside Claude, with checkboxes that work, a form that adds tasks, and a button that asks Claude to summarize the board — every step verified against the real server and the real View.

PNPriya NairResearch Editor · November 26, 2026 · 29 min read
TL;DR: MCP Apps (SEP-1865, stable since January 26, 2026) let an MCP server ship an interactive HTML View with a tool: the tool declares a ui:// resource, the host renders it in a sandboxed iframe, and the View calls tools back through the host. You build a task board with five tools — one the model sees, four only the UI can call — bundle the View into a single 239 KB HTML file, verify the whole contract with a real MCP client, and run it in Claude Desktop.
  • The pattern in one sentence: a tool declares _meta.ui.resourceUri pointing at a ui:// resource with MIME type text/html;profile=mcp-app; the host fetches it and renders it.
  • Two registrations do all the work: registerAppTool for the tool, registerAppResource for the HTML. The SDK is @modelcontextprotocol/ext-apps 2.0.4; Node 20+ required.
  • Visibility is the access control: visibility: ["app"] hides a tool from the model so only the View can call it — the four plumbing tools in this tutorial use it.
  • The View never talks to your server directly. Every call is relayed by the host over postMessage JSON-RPC, and the host applies a strict CSP by default.
  • Verified end to end: 18 protocol checks against the real server over stdio, an HTTP initialize handshake, and 15 View checks in a fake host — all passing.

Claude can already call your MCP tools. What it could not do — until MCP Apps — was show your user an interface instead of a paragraph. Ask for a chart and you got a description of a chart. Ask to review a list and you got the list as text, which you then had to re-type to change.

That gap closed in two steps. On January 26, 2026, MCP Apps became the first official extension to the Model Context Protocol: a standard way for a server to ship an interactive HTML interface with a tool, rendered in a sandboxed iframe inside the chat. On November 10, 2026, Anthropic went further, announcing full apps that open beside the conversation in Claude — with Claude able to operate the app itself. This tutorial builds one from scratch: a task board that lives inside Claude, with checkboxes that work, a form that adds tasks, and a button that asks Claude to summarize the board. Every line of it is verified — the server, the View, and the handshake between them all run in this tutorial’s test suite, and the outputs below are the real ones.

What you’ll need#

  • Node.js 20 or newer (this tutorial used 24.22.1) and npm. No other runtime, no Docker, no GPU.
  • A code editor and a terminal. Two terminal windows help in the final steps: one for the server, one for the tests.
  • A host to see it in. Claude Desktop, VS Code with MCP support, or the reference basic-host that ships with the ext-apps repo. The build itself needs no account and no API key.
  • Basic TypeScript. If you have built an MCP server before, this is a short step. If you have not, every piece is explained as it appears.
  • Cost: $0. Time: about 45 minutes.

The finished project is a folder called task-board-app with nine files: a server, an entry point, a View, three config files, and two test scripts. The server exposes five tools. One of them, open_board, is the tool the model sees. The other four — get_tasks, add_task, toggle_task, delete_task — are plumbing for the UI, hidden from the model entirely. Tasks persist in a tasks.json file, so the board survives restarts.

1. Scaffold the project#

Create the folder and install the dependencies from the official quickstart. The ext-apps SDK is the only new piece; the rest are the standard MCP TypeScript packages, zod for schemas, and Express for the HTTP transport.

2. Register the tool and the UI resource#

This is the whole pattern: a tool plus a UI resource, tied together by one URI. The tool’s _meta.ui.resourceUri names a resource under the ui:// scheme; that resource serves an HTML page with the MIME type text/html;profile=mcp-app. When a host calls the tool, it reads the resource and renders the page in a sandboxed iframe. The rest of the file is a small task store in tasks.json and four plumbing tools the View calls.

Three details deserve attention before you read the code. First, visibility: every tool defaults to visible to both the model and the app. Setting visibility: ["app"] hides a tool from the model, so only the View on this server connection can call it — that is how the four plumbing tools stay out of the model’s tool list. Second, every tool returns the board twice: human-readable text for the chat transcript, and structuredContent carrying the task list for the View. The app-only tools also put the same payload in their text as JSON, so the View can always read the new state even on a host that does not forward structuredContent to the View. Third, state lives in a file, not in memory: in HTTP mode the server factory runs once per request, and a View reload restarts from the HTML, so anything that must survive either belongs on disk.

import {
  registerAppResource,
  registerAppTool,
  RESOURCE_MIME_TYPE,
} from "@modelcontextprotocol/ext-apps/server";
import { McpServer } from "@modelcontextprotocol/server";
import { randomUUID } from "node:crypto";
import fs from "node:fs/promises";
import fsSync from "node:fs";
import path from "node:path";
import { fileURLToPath } from "node:url";
import { z } from "zod";

const HERE = path.dirname(fileURLToPath(import.meta.url));
// tsx runs server.ts from the project root; the compiled build runs it from dist/.
const PROJECT_ROOT = path.basename(HERE) === "dist" ? path.dirname(HERE) : HERE;
const DIST_DIR = path.join(PROJECT_ROOT, "dist");
const DATA_FILE = path.join(PROJECT_ROOT, "tasks.json");
const RESOURCE_URI = "ui://task-board/mcp-app.html";

interface Task {
  id: string;
  title: string;
  done: boolean;
  createdAt: string;
}

function seedTasks(): Task[] {
  const now = new Date().toISOString();
  return [
    { id: randomUUID(), title: "Ship the MCP App tutorial", done: false, createdAt: now },
    { id: randomUUID(), title: "Try the board in Claude Desktop", done: false, createdAt: now },
    { id: randomUUID(), title: "Read the MCP Apps spec (SEP-1865)", done: true, createdAt: now },
  ];
}

function loadTasksSync(): Task[] {
  try {
    return JSON.parse(fsSync.readFileSync(DATA_FILE, "utf-8")) as Task[];
  } catch {
    return seedTasks();
  }
}

function taskListText(tasks: Task[]): string {
  const open = tasks.filter((t) => !t.done).length;
  const done = tasks.length - open;
  const lines = tasks
    .map((t) => `${t.done ? "[x]" : "[ ]"} ${t.title}`)
    .join("\n");
  return `Task board: ${open} open, ${done} done.\n${lines || "(no tasks yet)"}`;
}

function boardPayload(tasks: Task[]) {
  return {
    tasks,
    openCount: tasks.filter((t) => !t.done).length,
    doneCount: tasks.filter((t) => t.done).length,
  };
}

/**
 * Creates a new MCP server instance with the task-board tools and UI resource.
 * Tasks live in tasks.json next to this file, so the board survives restarts
 * and is shared across transports (a fresh server is created per HTTP request).
 */
export function createServer(): McpServer {
  const server = new McpServer({
    name: "Task Board MCP App",
    version: "1.0.0",
  });

  let tasks = loadTasksSync();

  const persist = async () => {
    await fs.writeFile(DATA_FILE, JSON.stringify(tasks, null, 2), "utf-8");
  };

  // Every tool returns the same shape: human-readable text for the chat
  // transcript, plus structuredContent carrying the full task list for the View.
  const boardResult = () => ({
    content: [{ type: "text" as const, text: taskListText(tasks) }],
    structuredContent: boardPayload(tasks),
  });

  // The one tool the model can see. Its _meta.ui.resourceUri tells the host
  // to render the board UI whenever this tool runs.
  registerAppTool(
    server,
    "open_board",
    {
      title: "Open Task Board",
      description:
        "Open the interactive task board. Shows your tasks as a clickable list you can add to, check off, and delete.",
      inputSchema: z.object({}),
      _meta: { ui: { resourceUri: RESOURCE_URI } },
    },
    async () => boardResult(),
  );

  // Plumbing tools for the View. visibility: ["app"] hides them from the
  // model entirely — only the UI on this server connection may call them.
  // Their text payload is JSON so the View can always read the new state,
  // even on a host that does not forward structuredContent to the View.
  const jsonResult = () => ({
    content: [{ type: "text" as const, text: JSON.stringify(boardPayload(tasks)) }],
    structuredContent: boardPayload(tasks),
  });

  registerAppTool(
    server,
    "get_tasks",
    {
      title: "Get Tasks",
      description: "Return the current task list as JSON. Used by the board UI to refresh itself.",
      inputSchema: z.object({}),
      _meta: { ui: { resourceUri: RESOURCE_URI, visibility: ["app"] } },
    },
    async () => jsonResult(),
  );

  registerAppTool(
    server,
    "add_task",
    {
      title: "Add Task",
      description: "Add a task to the board. Used by the board UI.",
      inputSchema: z.object({ title: z.string().min(1).max(200) }),
      _meta: { ui: { resourceUri: RESOURCE_URI, visibility: ["app"] } },
    },
    async ({ title }) => {
      tasks = [
        ...tasks,
        {
          id: randomUUID(),
          title: title.trim(),
          done: false,
          createdAt: new Date().toISOString(),
        },
      ];
      await persist();
      return jsonResult();
    },
  );

  registerAppTool(
    server,
    "toggle_task",
    {
      title: "Toggle Task",
      description: "Flip a task between open and done. Used by the board UI.",
      inputSchema: z.object({ id: z.string() }),
      _meta: { ui: { resourceUri: RESOURCE_URI, visibility: ["app"] } },
    },
    async ({ id }) => {
      const task = tasks.find((t) => t.id === id);
      if (!task) {
        return {
          content: [{ type: "text" as const, text: `No task with id ${id}` }],
          isError: true,
        };
      }
      task.done = !task.done;
      await persist();
      return jsonResult();
    },
  );

  registerAppTool(
    server,
    "delete_task",
    {
      title: "Delete Task",
      description: "Delete a task from the board. Used by the board UI.",
      inputSchema: z.object({ id: z.string() }),
      _meta: { ui: { resourceUri: RESOURCE_URI, visibility: ["app"] } },
    },
    async ({ id }) => {
      if (!tasks.some((t) => t.id === id)) {
        return {
          content: [{ type: "text" as const, text: `No task with id ${id}` }],
          isError: true,
        };
      }
      tasks = tasks.filter((t) => t.id !== id);
      await persist();
      return jsonResult();
    },
  );

  // The UI resource: the bundled single-file HTML page, served with the
  // MCP Apps MIME type. prefersBorder asks the host for a visible frame
  // around the View; no CSP is declared, so the host applies its strict
  // default (no network fetches — everything the View needs is inlined).
  registerAppResource(
    server,
    "Task Board",
    RESOURCE_URI,
    {
      mimeType: RESOURCE_MIME_TYPE,
      _meta: { ui: { prefersBorder: true } },
    },
    async () => {
      const html = await fs.readFile(path.join(DIST_DIR, "mcp-app.html"), "utf-8");
      return {
        contents: [{ uri: RESOURCE_URI, mimeType: RESOURCE_MIME_TYPE, text: html }],
      };
    },
  );

  return server;
}

3. Start the server#

The entry point is the quickstart’s transport boilerplate, unchanged in structure: --stdio for Claude Desktop and VS Code, Streamable HTTP on port 3001 otherwise, in stateless mode (a fresh server per request, which is why the file-backed store from step 2 matters).

import { createMcpExpressApp } from "@modelcontextprotocol/express";
import { NodeStreamableHTTPServerTransport } from "@modelcontextprotocol/node";
import type { McpServer } from "@modelcontextprotocol/server";
import { StdioServerTransport } from "@modelcontextprotocol/server/stdio";
import cors from "cors";
import type { Request, Response } from "express";
import { createServer } from "./server.js";

/**
 * Starts an MCP server with Streamable HTTP transport in stateless mode.
 *
 * @param createServer - Factory function that creates a new McpServer instance per request.
 */
export async function startStreamableHTTPServer(
  createServer: () => McpServer,
): Promise<void> {
  const port = parseInt(process.env.PORT ?? "3001", 10);
  const app = createMcpExpressApp({ host: "0.0.0.0" });
  app.use(cors());

  app.all("/mcp", async (req: Request, res: Response) => {
    const server = createServer();

    const transport = new NodeStreamableHTTPServerTransport({
      sessionIdGenerator: undefined,
    });

    res.on("close", () => {
      transport.close().catch(() => {});
      server.close().catch(() => {});
    });

    try {
      await server.connect(transport);
      await transport.handleRequest(req, res, req.body);
    } catch (error) {
      console.error("MCP error:", error);
      if (!res.headersSent) {
        res.status(500).json({
          jsonrpc: "2.0",
          error: { code: -32603, message: "Internal server error" },
          id: null,
        });
      }
    }
  });

  const httpServer = app.listen(port, (err) => {
    if (err) {
      console.error("Failed to start server:", err);
      process.exit(1);
    }

    console.log(`MCP server listening on http://localhost:${port}/mcp`);
  });

  const shutdown = () => {
    console.log("\nShutting down...");
    httpServer.close(() => process.exit(0));
  };

  process.on("SIGINT", shutdown);
  process.on("SIGTERM", shutdown);
}

/**
 * Starts an MCP server with stdio transport.
 *
 * @param createServer - Factory function that creates a new McpServer instance.
 */
export async function startStdioServer(
  createServer: () => McpServer,
): Promise<void> {
  await createServer().connect(new StdioServerTransport());
}

async function main() {
  if (process.argv.includes("--stdio")) {
    await startStdioServer(createServer);
  } else {
    await startStreamableHTTPServer(createServer);
  }
}

main().catch((e) => {
  console.error(e);
  process.exit(1);
});

The script is where the protocol lives, and it is short enough to read in full. Four things to notice:

  • Handlers are registered before connect(). The host pushes the first tool result as soon as the tool runs; registering app.ontoolresult after connecting would miss it. The SDK warns you about exactly this.
  • The View never assumes how the host delivers data. extractBoard reads structuredContent first and falls back to parsing the text payload as JSON — the reason the app-only tools return JSON text.
  • Every user action is a tool call. A checkbox calls toggle_task; the form calls add_task; the delete button calls delete_task. The View holds no state of its own beyond what the server last returned.
  • sendMessage talks back to the chat. The summarize button posts a user-role message into the conversation, and the host decides what to do with it. Nothing in the View can force a model response — it can only ask.
import { App } from "@modelcontextprotocol/ext-apps";
import type { CallToolResult } from "@modelcontextprotocol/client";

interface Task {
  id: string;
  title: string;
  done: boolean;
  createdAt: string;
}

interface BoardPayload {
  tasks: Task[];
  openCount: number;
  doneCount: number;
}

const listEl = document.getElementById("task-list")!;
const countsEl = document.getElementById("counts")!;
const statusEl = document.getElementById("status")!;
const formEl = document.getElementById("add-form") as HTMLFormElement;
const inputEl = document.getElementById("new-task") as HTMLInputElement;
const summarizeBtn = document.getElementById("summarize-btn") as HTMLButtonElement;

const app = new App({ name: "Task Board", version: "1.0.0" });

let tasks: Task[] = [];

/** Pull the task list out of a tool result, however the host delivered it. */
function extractBoard(result: CallToolResult): BoardPayload | null {
  const structured = result.structuredContent as BoardPayload | undefined;
  if (structured?.tasks) return structured;
  const text = result.content?.find((c) => c.type === "text")?.text;
  if (!text) return null;
  try {
    const parsed = JSON.parse(text) as BoardPayload;
    return parsed.tasks ? parsed : null;
  } catch {
    return null;
  }
}

function render() {
  const open = tasks.filter((t) => !t.done).length;
  const done = tasks.length - open;
  countsEl.textContent = `${open} open · ${done} done`;

  listEl.innerHTML = "";
  for (const task of tasks) {
    const li = document.createElement("li");
    if (task.done) li.classList.add("done");

    const checkbox = document.createElement("input");
    checkbox.type = "checkbox";
    checkbox.checked = task.done;
    checkbox.setAttribute("aria-label", `Mark "${task.title}" ${task.done ? "open" : "done"}`);
    checkbox.addEventListener("change", () => void callTool("toggle_task", { id: task.id }));

    const title = document.createElement("span");
    title.className = "title";
    title.textContent = task.title;

    const del = document.createElement("button");
    del.type = "button";
    del.className = "delete";
    del.textContent = "✕";
    del.setAttribute("aria-label", `Delete "${task.title}"`);
    del.addEventListener("click", () => void callTool("delete_task", { id: task.id }));

    li.append(checkbox, title, del);
    listEl.append(li);
  }
}

async function callTool(name: string, args: Record<string, unknown>) {
  statusEl.textContent = "Working…";
  try {
    const result = await app.callServerTool({ name, arguments: args });
    const board = extractBoard(result);
    if (board) {
      tasks = board.tasks;
      render();
      statusEl.textContent = "";
    } else if (result.isError) {
      statusEl.textContent = "That didn't work — try again.";
    }
  } catch (error) {
    statusEl.textContent = `Error: ${error instanceof Error ? error.message : String(error)}`;
  }
}

function applyHostStyles() {
  const ctx = app.getHostContext();
  if (ctx?.theme) document.documentElement.dataset.theme = ctx.theme;
  const styles = ctx?.styles as Record<string, string> | undefined;
  if (styles) {
    for (const [key, value] of Object.entries(styles)) {
      if (typeof value === "string") {
        document.documentElement.style.setProperty(key, value);
      }
    }
  }
}

// The host pushes the open_board result as soon as the tool runs.
app.ontoolresult = (result) => {
  const board = extractBoard(result);
  if (board) {
    tasks = board.tasks;
    render();
  } else {
    // Fallback: ask the server directly for the current list.
    void callTool("get_tasks", {});
  }
};

// Theme can change while the View is open (host toggles light/dark).
app.onhostcontextchanged = () => applyHostStyles();

formEl.addEventListener("submit", (event) => {
  event.preventDefault();
  const title = inputEl.value.trim();
  if (!title) return;
  inputEl.value = "";
  void callTool("add_task", { title });
});

summarizeBtn.addEventListener("click", async () => {
  const open = tasks.filter((t) => !t.done).length;
  const done = tasks.length - open;
  const summary =
    `My task board: ${open} open, ${done} done. ` +
    (tasks.filter((t) => !t.done).map((t) => t.title).join("; ") || "Nothing open.");
  try {
    const result = await app.sendMessage({
      role: "user",
      content: [{ type: "text", text: `Summarize this for me: ${summary}` }],
    });
    statusEl.textContent = result.isError
      ? "The host didn't accept that message."
      : "Summary request sent to the chat.";
  } catch (error) {
    statusEl.textContent = `Error: ${error instanceof Error ? error.message : String(error)}`;
  }
});

// Connect to the host, then load the board. Handlers are registered above,
// before connect(), so the first tool result can't arrive before we're ready.
// Loading starts only after the handshake completes: callServerTool before
// that warns (and throws in a future SDK version).
app
  .connect()
  .then(() => {
    applyHostStyles();
    void callTool("get_tasks", {});
  })
  .catch((error: unknown) => {
    statusEl.textContent = `Could not connect to host: ${error instanceof Error ? error.message : String(error)}`;
  });

6. Verify the protocol#

Do not trust the build; talk to the server the way a host would. This script uses the official client SDK over stdio, spawns the compiled server, and asserts the whole contract: five tools, the UI link on open_board, app-only visibility on the plumbing tools, the resource’s MIME type and contents, the full mutation round-trip, an error case, and persistence on disk.

import fs from "node:fs";

  command: "node",

7. Verify the View#

The protocol checks prove the server. They say nothing about the View, which runs in a browser iframe talking postMessage. To test it without a host, this tutorial’s second script loads the bundled HTML in jsdom and plays the host: it answers the ui/initialize handshake, pushes the open_board result, then clicks the checkbox, submits the form, deletes a task, and presses summarize — asserting the DOM after each step. The heart of the fake host is small:

// Answer the handshake the way a real host does, then push the tool result.
if (msg.method === "ui/initialize") {
  respondToView(msg.id, {
    protocolVersion: "2026-01-26",
    hostInfo: { name: "fake-host", version: "1.0.0" },
    hostCapabilities: {},
    hostContext: { theme: "light", locale: "en-US", displayMode: "inline" },
  });
  setTimeout(() => {
    sendToView("ui/notifications/tool-result", boardResult());
  }, 50);
  return;
}
// Relay View-initiated tool calls to the same in-memory board.
if (msg.method === "tools/call") {
  const { name, arguments: args } = msg.params;
  if (name === "add_task") {
    tasks = [...tasks, { id: `t${Date.now()}`, title: args.title, done: false }];
  } else if (name === "toggle_task") {
    tasks = tasks.map((t) => (t.id === args.id ? { ...t, done: !t.done } : t));
  } else if (name === "delete_task") {
    tasks = tasks.filter((t) => t.id !== args.id);
  }
  respondToView(msg.id, boardResult());
  return;
}

The security model in 60 seconds#

Executing third-party HTML inside a chat client is exactly the kind of idea that makes security teams nervous, so the spec earns its keep here. Four rules cover most of what can go wrong:

  • The View never talks to your server directly. It lives in a sandboxed iframe on an origin the host controls, and every call is relayed by the host over postMessage JSON-RPC. The host can see, log, and refuse anything the UI asks for. Web hosts must additionally wrap the View in a sandbox proxy iframe on a different origin.
  • The default content security policy denies network access. Omit csp and the host applies a strict default, including connect-src 'none'. This board needs no network at all, so it declares none. If your View fetches an API, declare exactly that origin in csp.connectDomains on the resource — never on the tool, where hosts ignore it.
  • Visibility is the access boundary. A tool marked ["app"] is callable by the View on the same server connection and invisible to the model. A tool marked ["model"] is the reverse. The default is both. Put the resource URI on every tool the View calls, or the host has no UI to render for it.
  • State belongs on the server. When a View reloads, it starts from your HTML. The board keeps tasks in tasks.json for exactly this reason. And render task titles with textContent, never innerHTML — a task title is user input, and user input is not markup.

One more thing the November announcement adds, and one thing it does not. The new capabilities — app tools and embedded sites — invert the direction this tutorial uses: instead of the View calling the server, the View exposes tools the host calls (app.registerTool, ext-apps 1.7.0 or later), and a View can embed your real web product in an iframe. Both are in public preview for developers and, per Anthropic’s own docs, available to a limited set of organizations — build against them, but do not assume every Claude user will see them yet. What the announcement does not change is the stable core you just built: the January 2026 spec, the ui:// resource, and the handshake are the foundation the new features sit on.

Which approach should you use?#

Not every tool needs a UI. Pick by what the user has to do with the result:

ApproachUse it whenWatch out for
Plain MCP toolsThe answer fits in prose or JSON; no interaction neededNothing — this is still the right default
MCP Apps (this tutorial)The user must see, click, edit, or compare somethingHost support varies; keep the View a single file; state lives on the server
OpenAI Apps SDKYour users are on ChatGPTChatGPT-specific APIs; MCP Apps is the portable twin, built on the same patterns
MCP-UI (@mcp-ui/*)You want a production host/client frameworkHeavier; the official SDK already covers the server and the View
Claude app tools + embedded sitesClaude should operate your full web productPublic preview, limited organizations; embedded sites need frame-ancestors headers

The rule of thumb: if the user’s next action is obvious from the text, ship a tool. If the user’s next action is a click, ship an app.

The takeaway#

MCP Apps collapse the distance between “ask the model” and “use the software” into two registrations: a tool that declares a ui:// resource, and the resource itself. You built a board that renders inside Claude, calls tools back through the host, persists across reloads, and passes an 18-check protocol suite plus a 15-check View suite. The pattern generalizes to anything a chat window cannot show as text: dashboards, forms, calendars, canvases, media players.

Where to go next: rebuild the View with the React template from the ext-apps repo (examples/basic-server-react) and compare it with the vanilla version line for line; add an app tool with app.registerTool so Claude can add a task to the open board itself; or swap the file store for a database and serve the same app over HTTP. The repo’s examples folder — map, budget allocator, system monitor, sheet music, cohort heatmap — is the fastest way to see how far the pattern stretches.

Frequently asked questions

Do I need a paid Claude plan to use an MCP App I built?

No, not to build and test it: the reference basic-host, VS Code, and Goose need no plan at all. In Claude, the January 2026 connectors launched for Pro, Max, Team, and Enterprise; the November full-app rollout covers the web and desktop apps on all plans. The newest pieces — app tools and embedded sites — are a gated public preview, so a developer can build against them today without assuming every Claude user will see them yet.

My View renders blank. What do I check first?

Four things, in order: the tool’s _meta.ui.resourceUri must exactly match the resource URI (including the ui:// scheme); the resource must be served with the MIME type text/html;profile=mcp-app; the bundled HTML must be a single self-contained file with no external script or stylesheet references; and the host must support the extension — the verification script in step 6 catches the first three without any host at all.

Can the View fetch data from the internet or my own API?

Only if you declare it. The host applies a strict content security policy by default, including connect-src 'none'. List each origin in csp.connectDomains on the resource (never on the tool, where hosts ignore it), and keep anything the View needs at load time inlined in the bundle so it renders even with no network at all.
