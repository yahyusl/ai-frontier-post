Stop copying SKILL.md files by hand: the skills CLI is the package manager for agent skills

Agent skills spread by copy-paste: a SKILL.md here, a folder there, no record of where anything came from. Vercel’s skills CLI turns that into a real package workflow — install, lockfile, update, remove — across 79 coding agents, and every command in this tutorial was run and verified.

PNPriya NairResearch Editor · November 25, 2026 · 17 min read
TL;DR: Vercel’s skills CLI (1.9.0) installs Agent Skills from GitHub into any of 79 coding agents with one command, records each install in a versioned skills-lock.json with a SHA-256 content hash, and restores a whole project from that lockfile. This tutorial installs, verifies, updates, removes, and restores real skills — no API key, no account, no model calls.
  • skills 1.9.0, Node 22.20+: no install step beyond npx skills, no account, no API key — every command in this tutorial ran against the real CLI.
  • vercel-labs/agent-skills holds 9 skills; the React best-practices skill installed here carries 70 rules across 8 categories.
  • The lockfile hash is independently reproducible: the README’s test vector and the installed skill’s hash both check out byte-for-byte against a from-scratch implementation.
  • Project installs copy into the project; global installs land in ~/.claude/skills/; multi-agent installs keep one canonical copy under .agents/skills/ with per-agent symlinks.
  • Gotcha: unauthenticated GitHub API calls hit the rate limit and the CLI falls back to a full git clone — set GITHUB_TOKEN for the fast path.

Agent skills spread by copy-paste. Someone posts a good SKILL.md, you copy the folder into .claude/skills/, and six weeks later nobody can say where it came from, which version it is, or whether the copy in your other project is the same one. Multiply that by every coding agent you use — Claude Code, Cursor, Codex, OpenCode — each with its own skill directory, and the mess compounds. Vercel’s skills CLI is the package manager for that mess: one command installs a skill from GitHub into any of 79 supported agents, records the exact commit and a SHA-256 content hash in a skills-lock.json, and restores a whole project from that lockfile. It has 40,808 stars on GitHub, an MIT license, and 56 releases behind it.

This tutorial runs the whole workflow end to end. You will install the CLI, discover skills, install one into a project, verify the lockfile hash yourself with an independent implementation, install globally and across several agents at once, run the update lifecycle, use a skill without installing it, scaffold your own, and restore a project from its lockfile after deleting the installed files. Every command below was executed on this machine against skills 1.9.0, and every quoted output is the real output. No API key, no account, no model calls anywhere.

What you’ll need#

  • Node.js 22.20 or newer. The README’s minimum; the sandbox run used Node v24.22.1. Check with node --version.
  • No global install. Every command here runs through npx skills, which fetches version 1.9.0 on first use. Pin it if you want the exact version tested: npx -y skills@1.9.0 --version.
  • A project directory. Any folder works — the examples use an empty directory. Project installs write into it; nothing here touches your real home directory.
  • Optionally, a GitHub token. Unauthenticated GitHub API calls are rate-limited to 60 per hour per IP, and this CLI hits that limit fast on a shared network. Step 2 shows what happens — and the one-line fix.

One scope note before you start: no coding agent was installed in the sandbox, so the step where an agent invokes a skill is documented, not executed. What was verified is everything the CLI itself does: the files it writes, the directories agents read, the lockfile contents, and the hashes. If a step below says a file landed somewhere, that path was listed on disk.

Step 1: Install the CLI#

There is no installer. The first npx invocation downloads the package and runs it:

npx -y skills --version
# 1.9.0

Run --help next and read the whole surface before you install anything. The command list is short enough to memorize: add, use, remove, list, find, update, init, plus the experimental experimental_install and experimental_sync. The help text also documents the flags that make the CLI scriptable: -y skips confirmation prompts, --json emits machine-readable output, -a names the agents, -s names the skills, and -g switches from project scope to global scope. Every command in this tutorial uses -y and, where the output is quoted, --json — run the same commands without them in your own terminal and you get the interactive prompts instead.

Two environment variables are worth setting before anything else. The CLI collects anonymous usage data; DISABLE_TELEMETRY=1 or DO_NOT_TRACK=1 turns it off, per the README’s telemetry section. The sandbox runs for this tutorial used both:

export DISABLE_TELEMETRY=1 DO_NOT_TRACK=1

Step 2: Find a skill worth installing#

Skills live in GitHub repositories, and the directory is skills.sh. The CLI searches it with find. Searching for React skills owned by Vercel returns real install counts, which is the fastest quality signal the directory offers:

npx skills find react --owner vercel
Install with npx skills add <owner/repo@skill>

vercel/ai@ai-sdk 74.6K installs
└ https://skills.sh/vercel/ai/ai-sdk

vercel/chat@chat-sdk 5.6K installs
└ https://skills.sh/vercel/chat/chat-sdk

vercel/vercel-plugin@styled-jsx 3 installs
└ https://skills.sh/vercel/vercel-plugin/styled-jsx

vercel/vercel-plugin@streamdown 1 install
└ https://skills.sh/vercel/vercel-plugin/streamdown

For this tutorial the source is Vercel’s own skill collection, vercel-labs/agent-skills. List what a repository contains before installing anything — --list fetches the repo and prints the skills without writing a file:

npx skills add vercel-labs/agent-skills --list

The repo holds nine skills: deploy-to-vercel, vercel-cli-with-tokens, vercel-composition-patterns, vercel-optimize, vercel-react-best-practices, vercel-react-native-skills, vercel-react-view-transitions, web-design-guidelines, and writing-guidelines. The one this tutorial installs first is vercel-react-best-practices — React and Next.js performance guidelines from Vercel Engineering, 70 rules across 8 categories, which makes it a good test: a single SKILL.md plus a rules/ directory of supporting files, so the install has something to hash.

Expect one interruption on a shared network. The first fetch in the sandbox run hit the unauthenticated GitHub API rate limit, and the CLI said so plainly and kept going:

◇  GitHub API rate limit reached, falling back to git clone (slower)
│  Tip: run `gh auth login` or set GITHUB_TOKEN to use the fast path.

The fallback clones the whole repository instead of fetching the file listing through the API. It works, it is slower, and on a large repo it is noticeably slower. Set GITHUB_TOKEN — any token with public-repo read access, or gh auth login if you use the GitHub CLI — before a batch of installs, and the fast path returns. The rest of this tutorial ran with the fallback in place, so every timing-sensitive claim below already includes it.

Step 3: Install your first skill#

From your project directory, name the repository, the skill, the agent, and skip the prompts:

npx skills add vercel-labs/agent-skills \
  --skill vercel-react-best-practices -a claude-code -y --json
[
  {
    "name": "vercel-react-best-practices",
    "status": "installed",
    "source": "vercel-labs/agent-skills",
    "ref": null,
    "hash": "7991ed4fbecdac23f47c1a40c243e00a212a9e7f3604db93959b3ae11dffe299",
    "path": "/tmp/skills-cli-work/proj/.claude/skills/vercel-react-best-practices",
    "scope": "project",
    "agents": ["Claude Code"],
    "mode": "copy",
    "security": null
  }
]

Two fields in that output carry the whole design. scope: project means the skill belongs to this directory, not to your machine: the files were copied into .claude/skills/vercel-react-best-practices/ inside the project, and mode: copy means they are real files, not symlinks. A teammate who clones the project gets the skill with it. The second field is hash, the SHA-256 of the installed content — the same value the lockfile records, and the subject of the next step.

The install also wrote skills-lock.json in the project root. Read it — it is the entire point of using a package manager instead of copy-paste:

{
  "version": 2,
  "skills": {
    "vercel-react-best-practices": {
      "source": "vercel-labs/agent-skills",
      "commit": "5a37a6329fbad3666c3207392a6a7c0110e92efb",
      "sourceType": "github",
      "skillPath": "skills/react-best-practices/SKILL.md",
      "computedHash": "7991ed4fbecdac23f47c1a40c243e00a212a9e7f3604db93959b3ae11dffe299"
    }
  }
}

Five facts, each doing a job: where the skill came from, the exact commit it came from, that the source is GitHub, the path of the skill inside the repo, and the content hash. The commit matters most. A later reinstall fetches that commit, not the latest commit on the branch, so restoring a project a month from now reproduces the skill you tested — not whatever the repo looks like then. Only update moves the commit forward, which is Step 7.

Step 4: Verify the lockfile hash yourself#

A hash you cannot reproduce is a decoration. The README documents the exact algorithm, including test vectors, so verify it independently. The algorithm: collect every file in the installed skill folder, excluding metadata.json files and the .git, __pycache__, and __pypackages__ directories; normalize CRLF to LF in text files; sort the relative paths by their UTF-8 bytes; then feed each path, a NUL byte, the content length in decimal ASCII, another NUL byte, and the content into one SHA-256. Save this as verify_hash.py and run it against the installed skill:

"""Recompute a skills-lock.json computedHash from the installed files."""
import hashlib, os, sys

def computed_hash(root):
    entries = []
    for dirpath, dirnames, filenames in os.walk(root):
        dirnames[:] = [d for d in dirnames
                       if d not in ('.git', '__pycache__', '__pypackages__')]
        for f in filenames:
            if f == 'metadata.json':
                continue
            p = os.path.join(dirpath, f)
            rel = os.path.relpath(p, root).replace(os.sep, '/')
            entries.append((rel, p))
    entries.sort(key=lambda e: e[0].encode('utf-8'))
    h = hashlib.sha256()
    for rel, p in entries:
        data = open(p, 'rb').read()
        if b'\x00' not in data:
            data = data.replace(b'\r\n', b'\n')
        h.update(rel.encode())
        h.update(b'\x00')
        h.update(str(len(data)).encode())
        h.update(b'\x00')
        h.update(data)
    return h.hexdigest()

print(computed_hash(sys.argv[1]))
python3 verify_hash.py .claude/skills/vercel-react-best-practices
# 7991ed4fbecdac23f47c1a40c243e00a212a9e7f3604db93959b3ae11dffe299

The output matches the lockfile’s computedHash exactly. Before trusting the script, check it against the README’s own test vector: a folder containing only SKILL.md with the content # hi\n must hash to 93c36952d8843b33e68ae970ebabcc03e1687c9bb0dd1ecaf357060318952f55. It does — the script reproduces the vector byte-for-byte, so the match on the installed skill is a real verification, not a coincidence of two bugs. This is the check that makes the lockfile worth having: if a skill’s files are edited, renamed, or swapped after install, the hash stops matching, and list, check, and --frozen-lockfile can see it.

Step 5: Project skills vs global skills#

Project scope is the default, and it is the right default for skills tied to one codebase. Some skills belong everywhere: a deployment skill, a writing style, a review checklist you want in every repository. Add -g and the same command installs globally instead:

npx skills add vercel-labs/agent-skills \
  --skill deploy-to-vercel -a claude-code -g -y --json
[
  {
    "name": "deploy-to-vercel",
    "status": "installed",
    "source": "vercel-labs/agent-skills",
    "hash": "66b99dfa063b1c405155e9bffd99c04ca3e312e81b168d540b757bb194b7400a",
    "path": "/tmp/fakehome/.claude/skills/deploy-to-vercel",
    "scope": "global",
    "agents": ["Claude Code"],
    "mode": "copy"
  }
]

The global install lands in ~/.claude/skills/deploy-to-vercel, and the global lockfile lives at ~/.agents/.skill-lock.json — note the location: the user-level lockfile is inside ~/.agents/, not ~/.claude/. The path in the output above reads /tmp/fakehome/… because the sandbox run used an isolated home directory; on your machine it is your real $HOME. Keep the two scopes separate in your head: project skills travel with the repository and belong in version control alongside it; global skills belong to you and should never be committed to a project. The same skill can exist in both scopes at once, and list defaults to project scope — pass -g to see the global ones.

Step 6: One skill, every agent you use#

The reason to use a CLI instead of copying folders is that the folder layout differs per agent. Claude Code reads .claude/skills/, Cursor reads its own location, and so on across 79 supported agents. Pass several -a values and the CLI handles the mapping:

npx skills add vercel-labs/agent-skills \
  --skill vercel-composition-patterns -a claude-code cursor -y --json
[
  {
    "name": "vercel-composition-patterns",
    "status": "installed",
    "source": "vercel-labs/agent-skills",
    "hash": "f711ed8b16162eaa712abbcdbbae6c926f86c57e60127735fecc3ad0dd85b3fa",
    "path": "/tmp/skills-cli-work/proj/.agents/skills/vercel-composition-patterns",
    "scope": "project",
    "agents": ["Claude Code", "Cursor"],
    "mode": "symlink"
  }
]

Note the two differences from the single-agent install in Step 3. The path is now .agents/skills/vercel-composition-patterns, and the mode is symlink. With more than one agent to serve, the CLI keeps one canonical copy under .agents/skills/ and links each agent’s directory to it. On disk that looks like this:

.agents/skills/vercel-composition-patterns/   # the real files
.claude/skills/vercel-composition-patterns -> ../../.agents/skills/vercel-composition-patterns

One copy, every agent pointed at it — edit the canonical copy and every agent sees the change, and the lockfile hash still covers exactly one set of files. The --copy flag forces real copies instead of symlinks if your setup cannot follow them (some synced folders and network drives). The shorthand --all means --skill '*' --agent '*' -y: every skill in the repository into every detected agent, no prompts. Use it only on a repository you have already listed — --list first, as in Step 2.

Step 7: The lifecycle — list, check, update, remove#

Four commands cover the rest of a skill’s life. list shows what is installed and where it came from; --json makes the same listing scriptable:

npx skills list
# Project Skills
#
# vercel-react-best-practices ./.claude/skills/vercel-react-best-practices
#   Agents: Claude Code  Source: vercel-labs/agent-skills
npx skills list --json
[
  {
    "name": "vercel-react-best-practices",
    "path": "/tmp/skills-cli-work/proj/.claude/skills/vercel-react-best-practices",
    "scope": "project",
    "agents": ["Claude Code"],
    "source": "vercel-labs/agent-skills",
    "sourceType": "github",
    "renamedFrom": null,
    "status": "tracked"
  }
]

status: tracked means the installed files match the lockfile entry. check goes one step further and asks the source repository whether anything moved:

npx skills check
# Checking for skill updates…
# Updating for: Claude Code
# Checking 1 skill(s)…
# Fetching 1 source…
# ✓ All project skills are up to date

One honest quirk: check works, but it does not appear in skills --help. The README’s command table lists it; the installed 1.9.0 help text does not. The command exists and was verified — the help output is simply incomplete, and the README is the better reference for it. update is the command that acts on what check finds: it moves the lockfile’s recorded commit forward and re-installs. With nothing upstream to fetch, it reports the same clean result:

npx skills update -y
# Checking 2 skill(s)…
# Fetching 1 source…
# ✓ All project skills are up to date

Scope flags keep updates surgical: update -g touches global skills only, update -p project skills only, and naming skills — npx skills update vercel-react-best-practices — updates one. Removal is the mirror image, and it cleans up the lockfile entry as well as the files:

npx skills remove vercel-react-best-practices -y
# ◆  Successfully removed 1 skill(s)

After that removal, list shows one project skill left, and skills-lock.json holds one entry. The removal is complete: files gone, lockfile entry gone, no orphaned symlink left behind. Remove by name, or pass --all to clear everything — the flag implies -y, so do not combine it with named skills.

Step 8: Use a skill without installing it#

Sometimes you want a skill’s instructions once, for one prompt, without adopting it. use fetches the skill and prints the prompt your agent should run with it:

npx skills use vercel-labs/agent-skills@vercel-react-best-practices
You are being given a Skill to execute for the user's next request.

Use the following SKILL.md as your instructions:

<SKILL.md>
---
name: vercel-react-best-practices
description: React and Next.js performance optimization guidelines from Vercel
  Engineering. ...
---

# Vercel React Best Practices

Comprehensive performance optimization guide for React and Next.js applications,
maintained by Vercel. Contains 70 rules across 8 categories, prioritized by impact
to guide automated refactoring and code generation.

The output is the skill’s SKILL.md wrapped in <SKILL.md> tags, preceded by one line of framing. Pipe it into an agent — npx skills use vercel-labs/agent-skills@vercel-optimize | claude is the README’s example — or pass --agent claude-code and the CLI launches the agent with the skill itself. Without --agent it prints the prompt, which is the mode verified here: no agent binary existed in the sandbox, so the launch path is documented, not executed. Either way, nothing is installed and the lockfile is untouched, which makes use the right way to trial a skill before committing to it.

Step 9: Write your own skill with init#

The CLI also scaffolds new skills. init takes a name and writes the minimal valid skill:

npx skills init my-skill
./my-skill/SKILL.md
---
name: my-skill
description: A brief description of what this skill does
---

# my-skill

Instructions for the agent to follow when this skill is activated.

## When to use

Describe when this skill should be used.

## Instructions

1. First step
2. Second step
3. Additional steps as needed

That is the entire contract: a folder, a SKILL.md, and frontmatter with a name and a description that tells the agent when to load it. The description is the load-bearing line — agents decide whether a skill applies by reading it, so write it as a trigger (“Use when reviewing React components for performance”) rather than a summary (“React performance notes”). Run init with no name inside a skill folder to scaffold ./SKILL.md in place. From there the skill is yours to distribute: publish it in a repository and anyone can install it with skills add yourname/your-repo, and it appears on skills.sh for discovery.

Step 10: Restore a project from its lockfile#

The lockfile earns its keep when a project is cloned fresh — or when the installed files are deleted. Delete the installed skill directory but keep skills-lock.json, then restore:

rm -rf .claude/skills/vercel-react-best-practices
npx skills experimental_install
# ●  Linking to Claude Code
# ◇  Downloaded 1 source
# ◆  Restored vercel-react-best-practices

The skill comes back with the same hash as before — 7991ed4f…, the value recorded in Step 3 — because the restore fetches the commit pinned in the lockfile, not the latest commit on the branch. Check first with --dry-run to see what a restore would do without doing it, and use --force to reinstall skills that are already present. The command is still marked experimental, and its alias is the shorter skills install; in CI it defaults to --frozen-lockfile, which fails rather than changing the lockfile, so a build never silently drifts to a newer skill version. Commit skills-lock.json to version control and a teammate’s fresh clone is one skills install away from the exact skill set you tested.

One related experimental command is worth knowing by name and leaving alone for now: experimental_sync links skills shipped inside npm dependencies into your project, so a library can bundle instructions for your agent alongside its code. It was not exercised here — it needs a dependency that actually ships skills, and none was in scope — and its name and options may change without notice. Treat it as a preview, not a workflow.

Gotchas#

  • GitHub rate limits bite on shared networks. The CLI prefers the GitHub API for file listings; unauthenticated, that allowance is 60 requests per hour per IP. On a shared egress IP the limit is already spent when you arrive, and the CLI falls back to cloning the whole repo. The JSON output even records it: "fallback": {"reason": "rate-limited"}. Set GITHUB_TOKEN first.
  • check exists but --help hides it. The README lists it, the installed help does not. It works — Step 7 ran it — but if you only read --help you will never find it.
  • Project installs copy; multi-agent installs symlink. A single-agent project install writes real files into the agent’s project directory. Add a second agent and the CLI switches to one canonical copy under .agents/skills/ with symlinks. Both are correct; do not “fix” the symlink into a copy, or the two agents will drift apart on the next update.
  • --rename rewrites the skill. Installing with --rename my-design-rules installs the skill under the new name and rewrites the name: field in its SKILL.md frontmatter — verified by reading the file. That also changes its content hash, which the README documents: a renamed skill hashes as installed, not as published.
  • Scripts need -y. Without it, add prompts for the skill, the agents, and the scope. That is the right default for a human and the wrong one for CI; every command in this tutorial passes -y for exactly that reason.
  • Telemetry is on by default. Anonymous usage data only, per the README — but if that is not your policy, export DISABLE_TELEMETRY=1 or DO_NOT_TRACK=1 before the first run, not after.

When to use this vs alternatives#

ApproachUse it whenWatch out for
skills CLI (this tutorial)You use several coding agents, you want install/update/remove with a lockfile, or the skill set is shared across a teamNode 22.20+ required; GitHub API rate limits without a token
Copy the folder by handOne skill, one agent, one afternoon — and you will remember where it came fromNo version, no update path, no record; drift is silent
wshobson/agents plugin collectionYou want a curated bundle of plugins and skills installed in one move across harnessesYou get the bundle’s choices, not your own; covered in a separate AFP tutorial
skills.sh in the browserYou are browsing and comparing skills before committing to oneDiscovery only — installation still goes through the CLI or a manual copy
Agent’s built-in marketplaceYou live in one agent and its marketplace already carries the skillLocked to that agent; the same skill installed elsewhere is a second, untracked copy

The dividing line is the number of agents and the number of people. One skill in one agent is a file copy. Two agents, or a team sharing a project, is a package manager — and that is the point at which the lockfile starts paying for itself.

The takeaway#

Agent skills went from a curiosity to a dependency in a year, and the install story never caught up: folders copied from blog posts, no versions, no updates, no record. The skills CLI closes that gap with the least machinery possible — a GitHub source, a per-project lockfile with a reproducible content hash, and one command per lifecycle step. Install one skill into one agent today with npx skills add vercel-labs/agent-skills --skill vercel-react-best-practices -a claude-code -y, read the lockfile it writes, and verify the hash with the script in Step 4. If the hash matches, you have something copy-paste never gave you: proof that the skill on your disk is the skill its author published. Commit the lockfile, and the next person who clones the project gets exactly that — no archaeology required.

Frequently asked questions

Do I need Claude Code, or any agent, installed to use the CLI?

No. Installing, listing, updating, and removing skills only writes files into agent directories — the CLI never launches an agent for those commands. You need an agent installed only when you want the agent to actually invoke a skill. The sandbox run for this tutorial had no agent binary at all, and every install, list, check, and restore command still ran and was verified on disk.

Does installing a skill send my code anywhere?

No. An install fetches the skill repository from GitHub and writes files locally; your project code is never uploaded. The CLI does collect anonymous usage telemetry, which you can switch off with DISABLE_TELEMETRY=1 or DO_NOT_TRACK=1 before the first run.

What happens when the skill repository updates?

Nothing, until you ask. The lockfile pins the exact commit you installed, and reinstalls fetch that commit, not the latest one. skills check compares the pinned commit against the repository, and skills update moves the pin forward and re-installs.

Can I install a skill from a private repository?

The installation reference documents private-repository sources alongside the public GitHub path. Only the public path was tested here — vercel-labs/agent-skills is public — so treat the private-repo flow as documented, not verified in this tutorial.

What if two skills have the same name?

Install one of them with --rename. The CLI installs it under the new name and rewrites the name: field in the skill’s SKILL.md frontmatter, which was verified by reading the installed file. Note that renaming changes the content hash, so the renamed skill hashes as installed, not as published.
